# 架构与代码阅读顺序

## 先理解一条任务怎么走

用户输入 `/new` 直接创建任务；普通文本进入单独的 Router 线程。Router 只看近期聊天和任务摘要，不能访问文件或执行命令。它输出严格 JSON，程序校验后调用任务管理器。

创建任务时读取源仓库的当前提交，保存任务、首条输入、独立目录和初始状态。调度器从 `QUEUED` 任务中公平轮转，默认同时派发两个任务，每个任务最多有一个执行步骤在运行。

Worker 每次只完成一个步骤：准备目录、处理一个工具调用、把一个已完成结果加入会话，或者调用一次模型。步骤结束后，执行线程就可以处理别的任务。等待审批和等待人工回答都是数据库状态，不是在后台占着线程阻塞等待。

模型返回工具调用时，assistant 消息与所有工具调用一起保存。工具按模型返回顺序串行执行，按 `tool_call_id` 返回对应结果；一个 assistant 消息的全部工具结果进入会话后，才追加新的用户输入并调用模型。这避免生成不完整的工具调用协议历史。

如果模型直接交付最终文字，任务进入 `READY`，由用户检查并 `/accept`。模型完成时若有新补充已入库，继续处理补充，不提前停在待验收。

## 带依赖的计划如何执行

`TaskPlan` 调用模型生成计划并校验依赖，将节点按拓扑顺序保存。人工批准时，`Store.startPlan` 在同一事务里写入父任务与全部子任务。调度器分发依赖已冻结的子任务，并继续推进其它就绪分支。

`PlanExecution` 为每个子任务准备独立 Git 副本。副本只应用该节点的上游增量，内部提交固定有效基线。子任务交付后，以有效基线导出增量补丁并记录哈希。父任务用干净的原始基线逐一应用已冻结的增量。等待人工处理、执行中断和合成冲突均由持久化状态表示，合成重试使用新目录，保留旧现场。

CLI 和 `--serve-local` 共用 TaskManager、Router 和 Store。HTTP 入口使用回环地址和 Bearer 令牌，文件工具与补丁交付可用，命令工具关闭。独立的 GitHub 入口使用自己的配置和状态目录。

## 七个模块

| 包 | 负责什么 | 建议阅读 |
|---|---|---|
| `cli` | JLine 输入、命令解析、后台通知、退出 | `Main` |
| `router` | 自然语言输入的归属判断与校验 | `Router` |
| `task` | 任务状态、调度、取消、恢复、Git 副本与补丁 | `Task` → `TaskManager` → `Workspaces` |
| `worker` | 模型与工具循环、一次只推进一步、上下文治理 | `Worker` → `ContextPolicy` |
| `model` | 配置、HTTP 接口、JSON、离线模拟 | `ModelClient` → `HttpModelClient` → `DemoModel` |
| `tool` | 工具注册表、文件边界、Git 工具、结构化测试输出、Shell 与进程管理 | `ToolRegistry` → `FileTools` → `GitTools` → `Processes` |
| `storage` | 分表持久化、快照读、迁移、审计查询 | `Store` |
| `server` | HTTP 入口、指标与审计接口、GitHub 接入、发布 | `AgentServer` → `Service` → `Publisher` |
| `eval` | 评测数据集、判据引擎与报告 | `EvalRunner` → `EvalSuite` |

不使用框架自动组装依赖；`Main` 创建 Store、模型、TaskManager、Router。模型是一个很小的 `ModelClient` 接口，因此测试可直接注入确定性响应或阻塞响应，不需要真实 API。

## 为什么把状态集中保存

一次任务的状态变更和「下一步动作」必须在同一个事务里提交，所以 `Task` 仍然是一个完整的聚合对象：输入、工具调用、审批、计数、结果和验证记录都在里面。

区别在于**怎么存**。首版把整个 `Task` 序列化进 `tasks.data`，历史越长，每步重写的 JSON 越大。现在拆成两张追加表：

| 表 | 存什么 | 写入方式 |
|---|---|---|
| `tasks` | 骨架：状态、计划、审批、计数、结果、验证 | 每次状态推进重写（体积恒定） |
| `task_messages` | 对话消息 | 只追加，`seq` 单调 |
| `task_calls` | 工具调用及其结果 | 按 `seq` 覆盖写 |
| `events` | 审计事件 | 只追加，带类型与游标 |

因此调度只读骨架（`Store.skeleton` / `queued` / `list`），不反序列化对话；只有在真的要追加消息时才走 `updateConversation`。`get()` 读完整任务。

读路径不持锁：写连接串行（`ReentrantLock`），读走线程本地只读连接，靠 WAL 快照隔离。**一次读取必须在同一个快照里完成**——骨架与对话是两张表，两条独立语句之间若有写入提交，就会读到「旧骨架 + 新对话」的撕裂状态，所以 `load`/`select` 包在一个显式读事务里。

旧库打开时自动迁移：`PRAGMA user_version` 判断版本，先 `wal_checkpoint` 再复制一份 `state.db.v1.bak`，然后把整块 JSON 拆进追加表并回填 `status` 列。迁移幂等，可以重复执行。

调度不再每 30 毫秒空转全表：新建、补充、审批、取消、恢复、计划批准和「一个执行线程结束」都会显式唤醒调度线程，250 毫秒兜底轮询只用于覆盖遗漏的路径。

SQLite 仍是单写者。任务量继续增长时，下一步是把对话与事件表换成追加包并做分片，而不是继续加大单个数据库；当前不声称适合高并发服务端部署。

`router_history` 保存近期聊天的来源，Router 每次读取最近 12 条记录；任务摘要最多 50 个任务。这些是上下文范围限制，不是跨任务长期记忆。

## 上下文为什么必须治理

任务历史完整保存在数据库里，但送给模型的请求不能无界增长。`worker/ContextPolicy` 负责裁剪，规则有顺序：

1. `system` 提示与首条用户需求是锚点，永不裁剪——否则模型会丢失目标与验收约束；
2. 工具调用协议不可拆开：一条带 `tool_calls` 的 assistant 消息与其 `tool` 结果属于同一轮，整轮保留或整轮折叠；
3. 从最新一轮往前保留，放不下的早期轮次折叠成一条**确定性摘要**（抓取式：保留助手结论、调用过的工具名、工具结果片段），不伪造模型没说过的话；
4. 至少保留最后一轮，即使它单轮超预算——宁可超预算，也不能让模型看不到最近的工具结果。

预算默认 48000 token（按 2 字符 = 1 token 保守估算），可用 `SUPERAGENT_CONTEXT_TOKENS` 覆盖。折叠次数与最近一次请求的估算值记录在任务上（`contextTrims` / `contextTokens`），`/show` 会显示。

原始消息一条都不会被删除：裁剪只影响本次请求，不修改持久化历史。这样既控制了成本，又保留了完整审计与恢复能力。

## 命令审批为什么不能只写在提示词里

模型提出 `execute_command` 后，程序生成独立审批，保存完整命令、任务目录和调用 ID。没有这一条审批，工具代码不会启动进程。

用户批准时，TaskManager 校验审批是否仍属于任务当前等待的调用。Worker 再次核对命令和目录，把审批标记为已使用并记录执行意图，然后启动 Shell。旧审批不能给新命令复用。拒绝结果回到模型，而不是悄悄跳过。

实际命令、退出码、超时标记和完整日志路径保存在任务中。模型只能看到有限长度的输出，避免日志撑满上下文；原始输出保留在状态目录。

只读命令白名单默认关闭。开启后，明显只读的命令（`git status`、`mvn -v` 之类）免去人工点击，但审批记录与 `approval_auto_approved` 审计事件照样落库，最终 `decision` 为 `USED_AUTO`；含 shell 元字符或能间接执行外部程序的选项一律退回人工。`run_test` 永不自动批准。

同一原则用在改动范围上。提示词里写「需求不清楚先提问」不管用——真实运行里模型会用「项目里只有一处可优化的代码」推断范围然后直接改，这个推理还挺有道理。所以范围判定放在执行层：`task/ScopeGate` 检查需求原文（含用户全部补充）里有没有可定位的锚点（文件、`类.成员`、标识符、字面量、命令、目录），没有就拒绝 `write_file`/`edit_file`，把拦截写进验证记录，模型必须先 `ask_user`。用户补充了明确目标后闸门自动打开；计划子任务以人工批准的节点为准。默认严格，`SUPERAGENT_SCOPE_EXPLORATORY=1` 才是探索模式。

一句话原则：**凡是「安全属性」，都要能从代码里读出来，而不是从提示词里猜出来。**

## 恢复如何处理不确定性

外部动作和 SQLite 事务不能合成一个原子操作。最重要的故障窗口是：数据库已经记录“准备执行”，磁盘或命令的效果已经产生，但结果还没有保存。

对写文件与精确替换，执行前保存预期内容，恢复时读取文件进行核对。相同则说明目标写入已达成；不同就保留不确定提示，不能宣称成功。

对任意 Shell 命令，系统无法通用判断它有没有完成。故障后标记 `UNKNOWN`，用户检查并恢复时，只给模型补上“结果不明、不得自动重复”的工具结果，不重新启动原命令。若确实需要再次运行，必须形成新调用并重新审批。

模型调用遵循同一原则：只对「请求确定没有送达」的失败做有限重试（连接失败、连接超时、HTTP 429/503，默认 2 次、上限 5），因为重试这些不产生重复计费；请求超时和响应中断不重试，服务端可能已经处理并计费，重发会造成重复收费且掩盖真实状态。失败信息必须包含打到的地址、尝试次数和底层异常类型，否则运维只能猜。

取消先更新持久化状态，再中断当前线程并结束进程树。Worker 写回结果前必须核对任务仍在运行，因此迟到的 HTTP 结果不能把取消状态改成成功。新执行需要等旧步骤退出，避免两个 Worker 同时操作一个任务目录。

## 测试该怎么看

一条纪律：一个测试只有在「删掉被测逻辑后它必须失败」时才有价值。getter、常量、构造器一类不测。

先读 `KernelTest`：旧库迁移与幂等、对话追加顺序、回滚、调度载荷只取骨架、并发读不出现撕裂快照、审计游标。这些是存储内核的契约。再读 `RuntimeTest` 中的并行隔离与等待回复用例，然后读审批和取消用例。`HttpModelTest` 用本地 HTTP 服务检查真实请求的格式、usage、超时和中断。`RecoveryTest` 启动另一个 JVM，让外部命令产生文件后直接终止 JVM，再验证命令没有重放。`ContextPolicyTest` 验证预算裁剪不会破坏锚点与工具协议完整性。

`mvn test` 需要完整的进程与管道能力：在受限沙箱里 `git clone` 会因无法创建命名管道而失败，表现为大量「15 秒未达条件」的假失败。这类环境下请放宽沙箱或在 Linux CI 上运行，不要据此判断代码回归。

这些测试验证系统行为，不评价模型写代码的质量。真实编码质量、特定供应商接口兼容性与实际费用需要单独手工验收（见 `eval.md`）。
