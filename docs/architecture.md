# 架构与代码阅读顺序

## 先理解一条任务怎么走

用户输入 `/new` 直接创建任务；普通文本进入单独的 Router 线程。Router 只看近期聊天和任务摘要，不能访问文件或执行命令。它输出严格 JSON，程序校验后调用任务管理器。

创建任务时读取源仓库的当前提交，保存任务、首条输入、独立目录和初始状态。调度器从 `QUEUED` 任务中公平轮转，默认同时派发两个任务，每个任务最多有一个执行步骤在运行。

Worker 每次只完成一个步骤：准备目录、处理一个工具调用、把一个已完成结果加入会话，或者调用一次模型。步骤结束后，执行线程就可以处理别的任务。等待审批和等待人工回答都是数据库状态，不是在后台占着线程阻塞等待。

模型返回工具调用时，assistant 消息与所有工具调用一起保存。工具按模型返回顺序串行执行，按 `tool_call_id` 返回对应结果；一个 assistant 消息的全部工具结果进入会话后，才追加新的用户输入并调用模型。这避免生成不完整的工具调用协议历史。

如果模型直接交付最终文字，任务进入 `READY`，由用户检查并 `/accept`。模型完成时若有新补充已入库，继续处理补充，不提前停在待验收。

## 带依赖的计划如何执行

`TaskPlan` 调用模型生成计划并校验依赖，将节点按拓扑顺序保存。人工批准时，`Store.startPlan` 在同一事务里写入父任务与全部子任务。调度器分发依赖已冻结的子任务，并继续推进其它就绪分支。

`PlanExecution` 为每个子任务准备独立 Git 副本。副本只应用该节点的上游增量，内部提交固定有效基线。子任务交付后，以有效基线导出增量补丁并记录哈希。父任务用干净的原始基线逐一应用已冻结的增量。等待人工处理、执行中断和合成冲突均由持久化状态表示，合成重试使用新目录，保留旧现场。

CLI 和 `--serve-local` 共用 TaskManager、Router 和 Store。HTTP 入口使用回环地址和 Bearer 令牌，文件工具与补丁交付可用，命令工具关闭。独立的 GitHub 入口使用自己的配置和状态目录。

## 七个模块

| 包 | 负责什么 | 建议阅读 |
|---|---|---|
| `cli` | JLine 输入、命令解析、后台通知、退出 | `Main` |
| `router` | 自然语言输入的归属判断与校验 | `Router` |
| `task` | 任务状态、调度、取消、恢复、Git 副本与补丁 | `Task` → `TaskManager` → `Workspaces` |
| `worker` | 模型与工具循环，一次只推进一步 | `Worker` |
| `model` | 配置、HTTP 接口、JSON、离线模拟 | `ModelClient` → `HttpModelClient` → `DemoModel` |
| `tool` | 文件边界、文本工具、Shell 与进程管理 | `FileTools` → `Processes` |
| `storage` | SQLite 事务、进程锁、历史 | `Store` |

不使用框架自动组装依赖；`Main` 创建 Store、模型、TaskManager、Router。模型是一个很小的 `ModelClient` 接口，因此测试可直接注入确定性响应或阻塞响应，不需要真实 API。

## 为什么把状态集中保存

`Task` 是一份完整的任务记录，包含输入、会话、工具调用、审批、计数、结果和验证记录。首版把它序列化到 SQLite `tasks.data`，每次变更同时在 `events` 追加事件。这样可以直接保证“改状态”和“保存下一步动作”在同一个事务内完成，避免过早引入跨表协调。

Store 使用单连接、短事务和同步入口。读取返回重新反序列化的副本，后台线程拿不到可修改数据库中状态的共享引用。慢操作（HTTP、Git、Shell、文件工具）在数据库事务外执行。文件锁保护同一个状态目录，SQLite 使用 WAL 和 FULL 同步。

代价是任务历史越长，每步重写的 JSON 越大。首版以简单、易检查为目标；任务量增加后，可以在不改变任务接口的情况下把对话和工具结果拆成追加表。当前不声称适合高并发服务端部署。

`router_history` 保存近期聊天的来源，Router 每次读取最近 12 条记录；任务摘要最多 50 个任务。这些是上下文范围限制，不是跨任务长期记忆。

## 命令审批为什么不能只写在提示词里

模型提出 `execute_command` 后，程序生成独立审批，保存完整命令、任务目录和调用 ID。没有这一条审批，工具代码不会启动进程。

用户批准时，TaskManager 校验审批是否仍属于任务当前等待的调用。Worker 再次核对命令和目录，把审批标记为已使用并记录执行意图，然后启动 Shell。旧审批不能给新命令复用。拒绝结果回到模型，而不是悄悄跳过。

实际命令、退出码、超时标记和完整日志路径保存在任务中。模型只能看到有限长度的输出，避免日志撑满上下文；原始输出保留在状态目录。

## 恢复如何处理不确定性

外部动作和 SQLite 事务不能合成一个原子操作。最重要的故障窗口是：数据库已经记录“准备执行”，磁盘或命令的效果已经产生，但结果还没有保存。

对写文件与精确替换，执行前保存预期内容，恢复时读取文件进行核对。相同则说明目标写入已达成；不同就保留不确定提示，不能宣称成功。

对任意 Shell 命令，系统无法通用判断它有没有完成。故障后标记 `UNKNOWN`，用户检查并恢复时，只给模型补上“结果不明、不得自动重复”的工具结果，不重新启动原命令。若确实需要再次运行，必须形成新调用并重新审批。

取消先更新持久化状态，再中断当前线程并结束进程树。Worker 写回结果前必须核对任务仍在运行，因此迟到的 HTTP 结果不能把取消状态改成成功。新执行需要等旧步骤退出，避免两个 Worker 同时操作一个任务目录。

## 测试该怎么看

先读 `RuntimeTest` 中的并行隔离与等待回复用例，再读审批和取消用例。`HttpModelTest` 用本地 HTTP 服务检查真实请求的格式、usage、超时和中断。`RecoveryTest` 启动另一个 JVM，让外部命令产生文件后直接终止 JVM，再验证命令没有重放。

这些测试验证系统行为，不评价模型写代码的质量。真实编码质量、特定供应商接口兼容性与实际费用需要单独手工验收。
