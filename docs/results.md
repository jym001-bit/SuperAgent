# Super-agent Java 阶段成果

一页结论。所有数字都来自本机实际运行，未验证项单独列出。

## 它是什么

一个独立实现的 Java 编码 Agent：通过 CLI 或本地 HTTP 提交任务，Agent 生成带依赖的计划，**人工批准后**由多个 Worker 并行执行，交付一个可用 `git apply` 的总补丁。

不是 demo 的含义是：任务状态、审批、取消、恢复、补丁哈希全部持久化；进程被杀后不重复执行结果不明的命令；命令执行、发布、归档都有审计记录。参考了 DeepSeek 公开的 Super-agent 原型设计，不复制其源码。

## 六条核心设计

1. **持久化执行**：任务状态机（17 个状态）+ 骨架/对话分表。状态推进只重写骨架，对话按 `seq` 追加；调度只读骨架，长对话不会拖慢调度。旧库自动迁移并留备份。
2. **计划 → 依赖 → 合成**：计划节点按拓扑执行，每个子任务在独立 Git 副本里工作；下游先合入上游增量并冻结有效基线，父任务从原始基线按序合成，冲突保留现场可手工处理后重新导出。
3. **审批在执行层，不在提示词里**：命令逐次审批；只读命令白名单默认关闭，开启后免点击但**仍写审批记录与审计事件**；`run_test` 永不自动批准。
4. **恢复语义**：意图先存、执行、结果后存。写文件用「预期内容」回读核对；命令结果不明标记 `UNKNOWN` 且**绝不自动重放**。
5. **上下文治理**：送给模型的请求受预算约束，`system` 与首条需求是永不裁剪的锚点，工具调用按整轮保留，早期轮次折叠成抓取式摘要，原始消息一条不删。
6. **改动范围闸门**：需求指不出改哪个文件/类/方法时，写入工具由执行层直接拒绝，要求先澄清。理由见文末因果链第 4 条。

## 实测：自动化测试

`mvn test` → **95 个用例，0 失败 0 错误 0 跳过**。同一套测试在 GitHub Actions 上跑：`ubuntu-latest` × JDK 17 / 21 双矩阵，**两绿**，各 36 秒（Linux 比 Windows 快约 3 倍），覆盖编译、全量测试、fat jar 冒烟与备份脚本语法检查。测试原则是「删掉被测逻辑必须失败」，覆盖：

并发（两个模型请求同时在途）、崩溃恢复（子 JVM 执行外部命令后被 `Runtime.halt` 强杀，验证不重放）、迁移（v1 单表库升级与幂等）、规模（200 条对话 + 40 任务下调度载荷不含对话）、失败注入（模型错误、超时、连接失败重试分类、损坏的库被自检定位）、契约一致性（工具注册表与分派一一对应、指标与真实库一致）。

## 实测：真实模型（`deepseek-flash`）

9 个 golden task，每个任务独立临时仓库与状态目录，判据机械可判定。

| 运行 | 通过 | 原始通过率 | 传输层失败 | 平均调用 | 总 tokens |
|---|---|---|---|---|---|
| 第 1 次 | 6/9 | 66.7% | 2 | 6.67 | 130,791 |
| 第 2 次 | 8/9 | **88.9%** | **0** | 8.89 | 209,656 |

第 2 次之后传输层失败归零，唯一的残留失败是歧义需求任务。随后的两次单任务验证把它从「直接改代码」改成「提问 + 零改动」（见因果链第 4 条）；**闸门上线后全量 9 个任务还没有重跑过**，所以不要把 8/9 或单任务通过当成完整结论。

## 五个真实问题 → 修复 → 复验

这部分比功能清单更能说明工程质量：每个设计都对应一次真实故障。

| # | 现象 | 根因 | 修复 | 复验 |
|---|---|---|---|---|
| 1 | 受限沙箱里 20 个测试「15 秒超时」 | `git clone` 无法创建命名管道（`couldn't create signal pipe`），与代码无关 | 定位为环境限制并写入验收文档，CI 只在 Linux 跑 | 放宽沙箱后同批代码 33 个测试全绿，本轮结束 95 个 |
| 2 | 长任务越跑越慢 | 整个 `Task` 序列化进一个字段，每步重写全量 JSON | 拆成骨架 + 两个追加表，状态列走索引，读路径加显式读事务避免撕裂快照 | 长对话任务下 `queued()`/`list()` 不再反序列化对话，新增并发一致性用例 |
| 3 | 真实评测里 2/9 任务报 `ConnectException: null` | 连接失败一次都不重试，且错误信息无用 | 只对「请求确定未送达」的失败重试（连接失败/连接超时/429/503），超时与响应中断不重试以免重复计费；错误信息带地址、尝试次数、底层异常 | 同一数据集重跑，传输层失败 2 → 0 |
| 4 | 歧义需求「优化一下性能」被直接改代码 | 提示词管不住推断：模型先自造基准，改提示词后又改用「项目里只有一处可优化」推断范围 | 把范围判定移到执行层：需求无锚点时拒绝写入并留审计，用户补充目标后自动放行 | 该任务从 16 次调用/58,367 tokens（改文件）降到 7 次/12,391 tokens（提问 + 零改动） |
| 5 | 推送到 GitHub 后，CI 在 Linux 上 1/93 失败 | 关闭进程会打断 `git clone`，留下「目录存在但解析不出 HEAD」的半成品；旧实现在里面跑 git 必然报错，任务 `FAILED` 且 `/resume` 救不回来。Windows 因为慢，恰好没触发 | 副本准备区分「解析不出 HEAD」（重建）与「有效仓库」（保留并核对基线）；同时把测试里只报「15 秒未达条件」的断言改成打印任务真实状态 | 本地新增 2 个行为用例；Linux CI 复验**双 JDK 全绿** |

第 4 条的经验被写进架构文档：**凡是安全属性，都要能从代码里读出来，而不是从提示词里猜出来。**

第 5 条的教训是：**同一套测试换一个更快、文件系统语义不同的平台，能抓到本机跑一辈子也抓不到的缺陷**；而第一步不是猜，是先把「卡在哪」变成可读的信息——断言只报超时，排查就只能靠猜。

## 明确未验证的东西

- **容器链路**：本机未安装 Docker。镜像、compose、systemd 加固已交付并逐行复核，但**没有构建或运行过**。
- **真实 GitHub 端到端**：仍是本地 HTTP 与远端故障替身。
- **闸门的真实触发**：第 4 次运行是提示词生效、模型自行提问，范围闸门作为兜底**没有被真实模型触发**，其正确性目前由离线端到端用例覆盖。
- **长期稳定性**：真实模型只有 4 次运行（其中两次单任务），不能据此声称长期成功率，也不代表特定任务的成本上限。
