# Java 用户名校验案例

需求是把只检查空白的用户名校验改为明确的规则。用户名为 `null` 时返回 `false`，允许 ASCII 字母、数字和下划线，长度为 3 到 16，边界包含。空格、标点和非 ASCII 字符均不通过。

[案例基线源码](../examples/username-validation/pom.xml)

## 实际完成的验证

| 步骤 | 结果 |
|---|---|
| 原仓库运行 Maven | 原有 2 个测试通过。 |
| 只把新测试放进原实现的副本 | 6 个测试中有 2 个断言失败、1 个空指针错误，证明新增测试能发现旧行为。 |
| CLI 按计划执行 | 实现节点先完成，测试节点读到上游改动后编写测试。CLI 记录逐条审批，实际 `mvn -B -o test` 退出码为 0。6 个测试全部通过。 |
| 验证交付 | 总补丁通过 `git apply --check`。应用到另一份干净副本后，6 个测试再次通过。源仓库的提交和工作区保持原样。 |
| 冲突演练 | 两个独立节点分别把同一校验改成 3–16 和 5–20。合成在第二个补丁暂停，保留合成目录和各子补丁。按原规则手工处理后，`/resolve` 重新导出的补丁通过可应用性检查。 |

这个案例使用确定性的本地 HTTP 模型替身。CLI、Git、SQLite、命令审批和 Maven 都实际运行。替身返回固定的计划与工具调用，方便单独验证执行框架。

## 真实模型复验

真实 DeepSeek 已在 `username-real-state` 生成实现和测试两份补丁。审查确认只修改了用户名校验实现与测试。在干净副本中依次应用两份补丁，运行 `mvn -B -o -Dtest=UsernameValidatorTest test`，30 个用例全部通过，退出码为 0。把同一批新测试放回旧实现后，得到 18 个断言失败和 1 个错误。

原任务通过 CLI 正式审批后，在验证 Worker 的副本再次运行同一 Maven 命令。30 个用例全部通过，退出码为 0。合成的总补丁与独立复验补丁内容一致，并通过原始仓库的 `git apply --check`。父任务已验收为 `COMPLETED`。

这次复验还发现了一个审批交互问题。规划把“获批后执行”拆成了“只提出命令”，Worker 随后用普通提问等回复。规划器和 Worker 已明确区分两种情况。需要执行时由 `execute_command` 发起正式审批，用户只要命令建议时交付文本。用真实模型复测，新计划明确使用该工具发起正式审批，获批后记录退出码。已经生成的计划仍可用 `/follow` 给验证子任务补充指令。

## 复现

在 Super-agent 项目根目录运行。需要 Java、Git、Maven 和 Node.js。先完成 Maven 打包，让本地缓存具备离线测试依赖。

```powershell
mvn package
node .\scripts\verify-username-case.cjs
```

命令打印生成目录 `target/username-case-*`，其中 `source` 是独立测试仓库，`review` 是应用总补丁后的结果，`cli.log` 是完整交互记录，`evidence.json` 标出补丁和 Worker 的 Maven 日志。`maven-review.log` 记录应用补丁后独立运行的结果。演示脚本只批准固定替身提出的测试命令。

如果用真实模型复验，在 PowerShell 给本地进程配置自己的 Key，使用上述生成的 `source` 目录并换一个状态目录启动 CLI。可输入以下需求：

```text
/plan 完善 UsernameValidator：null、空白、非 ASCII 字符和非法标点返回 false，只允许 ASCII 字母、数字和下划线，长度 3 到 16（含）。先改实现，再由依赖它的子任务补边界测试。只改实现和测试这两个文件。提出 Maven 测试命令，等待我的批准。
```

检查计划再 `/start`。测试日志有退出码后，查看总补丁再 `/accept`。这一步单独评价真实模型能否完成该需求。

## 两分钟面试讲法

我做了一个 Java 编码 Agent，给它一个目标，Router 会生成带依赖的计划，用户批准后才分发给 Worker。比如这次用户名校验，我把实现和测试拆开。实现节点先生成补丁，系统把补丁应用到测试节点的独立 Git 副本，所以测试节点看到的是新实现。它请求执行 Maven 时，系统会暂停并记录审批，批准后才运行。

交付时，父任务从原始提交开始，按依赖顺序把每个节点自己的增量合成一次。这个案例中，新测试在旧实现上发现了空指针和规则漏洞。应用总补丁后，6 个测试通过。我还让两个独立节点故意改同一行，验证合成冲突会保留现场，并能在手工处理后重新导出。

| 面试追问 | 回答要点 |
|---|---|
| 为什么下游补丁不会重复包含上游改动？ | 先把依赖补丁应用到下游副本并固定有效基线。下游只导出相对有效基线的变化，父任务按拓扑顺序应用每个增量一次。 |
| 独立 Worker 同时改同一行怎么办？ | Git 应用补丁时检测到无法合入，父任务暂停。保留各节点的补丁和合成目录，交给操作者决定最终内容。 |
| 你怎么证明测试确实在验证需求？ | 先用同一批测试跑旧实现，观察到两次断言失败和一次空指针。应用最终补丁后在干净副本上再跑，六项都通过。 |
| 模型出错和框架出错怎么区分？ | 这次用确定性的模型替身控制输入，检查任务调度、审批、补丁与测试链路。真实模型处理业务需求需要另外验收。 |
